# レイアウト変更時の構造不一致エラー表示

進捗管理用の作業台帳 — **完了したら削除ないし`todo/archive/`へ移動する**。

発端はユーザー指摘: 「レイアウトを変更するときに、選択できないレイアウト
ならばエラーを出してほしい」。ユーザーに確認したところ、想定しているのは
**スライドの内容(title/body/codeなどのスロット)と、選んだレイアウトの
構造が一致しないケース**(peitho-coreがビルド時に弾く組み合わせ)。

## スコープ

- **目的**: 内容と構造が合わないレイアウトを選んだ際、ビルド失敗として
  間接的に気づく現状から、選択の場でエラーとして分かるようにする。
- **やらないこと**: 存在しないレイアウト名の参照(手編集・外部インポート
  由来)の検出、レイアウトの自動修復・スロット構成の提案機能。
- **受け入れ条件**: 方式(A)/(B)いずれであれ、構造不一致なレイアウトを
  選んだときユーザーにその場でエラー(またはロールバック+通知)が伝わり、
  デッキが壊れた状態のまま保存され続けることがない。

## 背景

- `SlideContextMenu.tsx`の「Change Layout」submenuは`layoutPreviews`
  (`previewLayouts` IPC)の一覧から選ぶだけで、選択時の構造チェックは
  一切ない。
- レイアウト変更自体は`components/Studio.tsx`の`changeSlideLayout` →
  `updateSlideConfig` → 通常の`commitChange`経路を通る。構造不一致は
  今のところ「保存後にビルドが失敗し、`StatusBar`の`errorMessage`に
  出る」という間接的な形でしか分からない。

## 要調査

- peitho-core(`crates/peitho-core/src/theme.rs`/`layout.rs`)に、
  「このスライドの内容が指定レイアウトのスロットと合致するか」を
  レンダリングを実行せずに事前判定できる関数があるか確認する。
  なければ新設が必要か、既存の`render`パスを流用した検証しかできないかを
  見極める。

## 方針候補(要 Fable 相談 — 実装規模がかなり違う)

- **(A) 変更を実行してからエラーを検知する**: 通常の`commitChange`経路で
  レイアウトを変更し、結果`errorMessage`が立ったら「構造不一致」だったと
  判断して元のレイアウトへ自動ロールバックし、メニュー上にその場で
  エラーメッセージを出す。実装コストは小さいが、一瞬でも不正な状態で
  保存が走る・エラー文言がビルドエラーそのままで分かりにくい可能性。
- **(B) 選択前に事前検証する**: レイアウトピッカーを開いた時点で各候補を
  事前チェックし、合致しないものは選択肢自体をdisabled表示にする。
  UXは良いが、peitho-core側に検証専用の窓口がなければ新設が必要になり
  スコープが一気に広がる。

このファイルは実装着手前に、上記どちらの方式にするか・peitho-core側の
検証手段の有無を確認してから着手すること。
