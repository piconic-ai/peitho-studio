# <タイトル>

進捗管理用の作業台帳 — **完了したら削除ないし`todo/archive/`へ移動する**。

発端: <ユーザーの要望を要約。壁打ちで意味を確定させた場合はその結論も>

## スコープ

- **目的**: このタスクが達成しようとしていることを1〜2文で。
- **やらないこと**: 意図的に手を出さない範囲。自律ループが「ついでに」
  手を広げるのを防ぐ柵として機能させる — 関連はするが別タスクとして
  切り出すべきものをここに列挙する。
- **受け入れ条件**: 「これが真になったら完了」と言える、検証可能な状態。
  曖昧な形容詞(「使いやすく」「きれいに」)ではなく、観測可能な事実で書く。

## 背景・要調査

実装前に確認しておくべき、既存コードの制約や未知の事実。「読めば分かる
はず」で済ませず、実際に読んで分かったことをここに書く。読まずに書いた
推測は推測だと明示する。

## 方針

複数の実装候補がありうる場合は列挙し、決め手/未決着なら何を根拠に
決めるか(誰に相談するか)を明記する。特定の1案に決め打ちできるなら
その理由も一言添える。

## レイヤー配置

domain/state/ipc/dom/components(フロント)、engine/peitho.rs/lib.rs
(Rust)のどこに何を置くか。

## テスト

新規/変更する純粋関数ごとに、spec(典型入力)とadversarial(境界値・
不正入力・空文字)の両方を書く前提で、対象を具体的に挙げる。

## 完了条件

自動で確認できる項目(ループが自分で判定してよい):
- [ ] `bun test` / `bun run typecheck` グリーン
- [ ] (Rust変更があれば) `cargo test` グリーン
- [ ] <その他、コマンド一発で真偽が決まる項目>

人間の判断が必要な項目(ここに到達したら一旦止めて委ねる):
- [ ] 実機(`run-peitho-studio` skill)での見た目/挙動確認
- [ ] <設計方針の最終確認など、コードだけでは決まらない項目>

## 先送り事項

実装中に見つかった、本筋と無関係な改善点はその場で直さずここに書き出す。
別タスクとして価値があるものは、実装完了後に新規`todo/*.md`として切り出す
(このファイルの中に埋もれたままにしない)。
