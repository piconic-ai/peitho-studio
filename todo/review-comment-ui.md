# プレビューのコメントUI

進捗管理用の作業台帳 — **完了したら削除ないし`todo/archive/`へ移動する**。

発端: ユーザーとの設計相談(2026-09-28)。Coding Agentへの依頼を、プレビュー
上で「気になる箇所をクリックしてコメントを書き、まとめて送る」形にしたい。
参考はClaude Designのコメント(要素にピンが立ち、その横に
`Slide 1 › Display "Presentation title"`のような対象の表示と入力欄、
「Claudeに送信」のチェックがある)と、crit(コメント → エージェントが直して
返信 → 不満ならレスを返す、という往復)。critのlive画面を実際に試し、往復は
最高だが、スライド移動(Navigate)とコメント(Pin)のモード切替が面倒、と
いう評価だった。**Studioではスライド一覧で移動できるので、プレビューは
モード切替なしでコメントできるようにする。**

3本組のうちの1本(UIの側)。往復の仕組みは`todo/crit-review-bridge.md`
(**先に進める**)、デッキに置くエージェント向け指示は
`todo/deck-agents-md.md`。

## スコープ

- **目的**: プレビューの要素をクリックしてコメントを付け、ためたコメントを
  エージェントに送り、エージェントの返信をそのコメントのスレッドとして
  見られるようにする。
- **やらないこと**:
  - critとの通信・同梱(`todo/crit-review-bridge.md`)。
  - 範囲をドラッグして囲むコメント、スクリーンショットの添付。第1段階の
    後で検討する(「先送り事項」)。
  - サムネイルへのピン表示(件数のバッジは入れる)。
  - コメントを解決済みにする以外の管理(削除・編集の履歴など)。
  - スピーカーノート欄へのコメント。
- **受け入れ条件**:
  - プレビューでは、モードを切り替えずに、段落・見出し・リストの項目・表の
    セルをクリックするとピンが立ち、入力欄が開く。入力欄の上に
    `Slide N › 種類 "本文の頭"`の形で対象が出る。
  - ピンのない場所(画像、コードブロック、レイアウトの飾り)をクリックした
    ときは、スライド全体へのコメントになる。
  - コメントには`deck.md`の行範囲と元のMarkdown(引用)が結びつき、送信時に
    それが`todo/crit-review-bridge.md`のコマンドに渡る。
  - コメントを付けたスライドのサムネイルに件数が出る。
  - 「送信」で未送信のコメントがまとめて送られ、エージェントの返信が来ると
    該当コメントの下に表示される。返信に対してさらにコメントできる。
  - 送信先のセッションがない(エージェントが待っていない)ときは、送信
    ボタンが押せず、その理由と、エージェントに何と頼めばよいかが出る。
  - 本文の編集で行がずれても、送信前のコメントは同じ要素を指し続ける。

## 背景・要調査

実際に読んで分かったこと:

- **クリックした要素 → ソースの対応づけ**: peitho-coreには、プレビュー上の
  編集のための描画モード`EditAnnotations::On`がある(`peitho`の
  `crates/peitho-core/src/render.rs`)。段落・見出し・リストの項目
  (tight list)・表のセルの要素に
  - `data-peitho-src="開始-終了"`: パーサーに渡したソースの**UTF-8のバイト
    位置**(includeの展開とBOMの除去の後、frontmatterを含む)
  - `data-peitho-md="…"`: その範囲の元のMarkdown(HTML属性用にエンコード
    されている)
  が付く。Studioは今`EditAnnotations::Off`で描画している
  (`src-tauri/src/engine/pipeline.rs`の`render_deck`呼び出し)。
- JSの文字列はUTF-16なので、バイト位置をそのまま`deck.md`の文字位置や行に
  使えない。変換が要る。
- includeを使うデッキでは、バイト位置が展開後のソース基準になり、
  `deck.md`の行とずれる。
- レイアウトのHTMLに`data-peitho-src`/`data-peitho-md`が既に書かれていると
  peitho-coreが検出する処理がある(`find_edit_annotation_attribute`)。
  Onにしたとき、そういうレイアウトがエラーになるか確かめる。
- **プレビューの作り**: `components/SlidePreview.tsx`が
  `dom/slideCanvas.ts`の`mountSlideCanvas(..., 'interactive')`でShadow DOMに
  描く。同じ文書なので、クリックを拾うのは容易。今はShadow root上の
  captureリスナーで`<a href>`のクリックだけを止めている。サムネイルは
  `'thumbnail'`モードで、クリックの対象にならない。
- **同じ断片をサムネイルと共有**: 描画結果の断片はサムネイルとプレビューで
  同じもの。Onにすると両方に属性が付く(見た目は変わらないはず)。
- critのlive画面では、ピンがスライドの`<section>`にしか付かなかった
  (Shadow DOMの中に入れない)。エージェントには`data-slide-key`が渡り、
  スライド単位の依頼には足りたが、要素単位には足りなかった。

要調査(着手時に確かめる):

1. `EditAnnotations::On`にしたとき、既存のテスト・e2e・見た目(レイアウト
   のCSS/JSが属性に反応しないか)に影響がないか。レイアウトのJSが作る
   要素(グラフなど)はピンの対象外になるので、スライド全体へのコメントで
   受ける。
2. モード切替なしでクリックをコメントに使うと、プレビュー上のテキスト選択
   や、レイアウトのJSが作る操作できる要素(グラフのツールチップなど)と
   ぶつからないか。ぶつかるなら、ドラッグ(テキスト選択)とクリックを区別
   する、またはShift+クリックなどに寄せる。ユーザーは**モード切替を
   面倒と評価した**ので、切替ボタンは最後の手段にする。
3. `data-peitho-md`のデコード方法(`encode_edit_markdown_attribute`の逆)。

## 方針

- プレビューだけ`EditAnnotations::On`で描く(Rust側で描画時に切り替える
  か、常にOnにするかは要調査1の結果で決める)。
- ピンの位置は、クリックした要素の`data-peitho-src`から「`deck.md`の行範囲 +
  引用」を作る。属性のない場所はスライド単位(スライドのキーと番号)に
  する。コメントの識別は、スライドのキーと引用で行う(critのコメントIDは
  巡ごとに振り直されるため、`todo/crit-review-bridge.md`参照)。
- 対象の表示(`Slide 2 › heading "Markdown is the source"`)は純粋関数で
  作り、コメント本文の先頭にも付けてエージェントに渡す(エージェントが
  どの要素のことか分かるように。試行では`[Slide 2 › heading] …`の形で
  伝わった)。
- 未送信のコメントはStudioの中に保持し、送信でまとめて
  `todo/crit-review-bridge.md`のコマンドに渡す。送信後の状態(返信・解決)は
  critの側を正とし、イベントで読み直す。
- 入力欄はプレビューの上に重ねる。`window.prompt()`は使わない
  (WKWebViewで不安定、CLAUDE.md)。

## レイヤー配置

- Rust
  - `engine/pipeline.rs`: 描画時の`EditAnnotations`の切り替え。
- フロント
  - `domain/reviewComment.ts`(新規): コメントの型、`data-peitho-src`の
    バイト位置 → 行範囲の変換、`data-peitho-md`のデコード、対象の表示の
    文字列、編集後に引用で位置を取り直す関数、スライドごとの件数。
  - `state/`: 未送信のコメントと、critから読み直したスレッドの保持
    (`Map`を1つのsignalに入れない — BarefootJSの落とし穴、CLAUDE.md)。
  - `dom/`: Shadow root内のクリックから対象の要素と属性を取り出す処理、
    ピンと入力欄の位置合わせ。
  - `components/`: ピン・入力欄・コメント一覧(スレッド)・送信ボタン・
    サムネイルの件数。
  - `domain/messages.ts`: 文言(英語・日本語)。

## テスト

- `domain/reviewComment.ts`
  - バイト位置 → 行範囲: spec(ASCIIだけの文書)、adversarial(日本語など
    マルチバイト、絵文字(サロゲートペア)、CRLF、範囲が文書の外、開始>終了、
    空文字、frontmatterあり)。
  - デコード: spec(改行を含むMarkdown)、adversarial(`&quot;`などの
    エンティティ、空、壊れた値)。
  - 対象の表示: spec(見出し・段落・リストの項目・表のセル・スライド全体)、
    adversarial(本文が長い、空、改行を含む)。
  - 位置の取り直し: spec(前に行を足した)、adversarial(引用が消えた、
    同じ引用が2か所ある)。
- e2e(`e2e/`、`mockTauri`): 描画のモックが`data-peitho-src`付きの断片を
  返す前提で、クリック → 入力 → サムネイルの件数 → 送信(コマンドのモック
  が呼ばれ、行範囲と引用が渡る)→ 返信のイベント → スレッド表示。
  セッションがないときに送信ボタンが押せないこと。
